# 0.1.51 — recover the status-light driver after a retained fault

The device could stop the LED driver with timeout5 while the LED ring retained
its last blue frame. HA also treated that retained fault as rejection of supply
confirmation, preventing the subsequent enable command from restarting it.

Read-only status and supply confirmation now accept a retained driver fault;
explicit operation failure still rejects the request. Enable must return a
started, enabled, error-free driver and confirmed supply. A fresh driver fault
keeps the existing status-light switch available for recovery; brightness remains
unavailable until recovery. No additional entities or controls.

Accepts exact16-byte v1 or40-byte v2 status responses. v2 adds bounded transfer
latency/fault context to the existing internal snapshot, preserving per-device
nonce/operation matching. Retired long diagnostic payloads remain rejected.

Validation:92 pytest tests, Ruff, integration package build. Tests cover old
fault recovery, failed restart, availability, exact wire lengths and versioning.
HA2026.10.4/ZHA target installation and LED physical acceptance follow publication.

starts its timeout after DMA submission; target cause verification remains pending.
